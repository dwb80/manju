# Manju 前端交付验收规范

> 版本：v1.0  
> 日期：2026-07-28  
> 适用范围：`frontend/`（Next.js 15、React 19、TypeScript）  
> 状态：正式规范

## 1. 目的

本规范用于判断一个前端功能、页面或版本是否达到可提测、可发布、可交付状态。

它不重复定义视觉样式或领域规则，而是把产品功能、UI、API 集成、异常处理、质量和生产构建统一成可验证的交付门禁。

配套权威文档：

- UI、交互和组件实现遵循 [`../ui-design-improvement-spec/ui-design-improvement-spec.html`](../ui-design-improvement-spec/ui-design-improvement-spec.html)。
- 领域边界和跨上下文协作遵循 [`ddd/README.md`](ddd/README.md)、[`ddd/contracts.md`](ddd/contracts.md) 和 [`ddd/dependency-rules.md`](ddd/dependency-rules.md)。
- 页面与限界上下文映射遵循 [`ddd/module-map.md`](ddd/module-map.md)。

出现冲突时按以下原则处理：

1. 产品验收条件决定“做什么”；
2. DDD 和 API 契约决定“业务语义与数据是什么”；
3. UI 规范决定“如何呈现与交互”；
4. 本规范决定“何时可以交付”。

## 2. 规范级别

- **必须（MUST）**：未满足即阻断交付。
- **应该（SHOULD）**：默认满足；例外必须记录原因、风险、责任人和补偿措施。
- **可以（MAY）**：根据页面复杂度选择。

## 3. 交付判定

一个前端版本只有同时满足以下条件才可判定为“可交付”：

- 所有 MUST 项通过；
- 没有未处置的 P0/P1 缺陷；
- P2 缺陷已有明确评估，不影响核心流程；
- 自动化质量门禁通过；
- 关键页面完成人工验收；
- 所有例外均有书面记录。

单个页面视觉完成、接口正常返回或生产构建成功，均不能单独代表前端已经可交付。

## 4. 功能完整性门禁

### 4.1 页面与需求

- [ ] MUST：页面可以追踪到明确的产品需求或验收条件。
- [ ] MUST：页面所属限界上下文与 `docs/ddd/module-map.md` 一致。
- [ ] MUST：核心操作的入口、成功结果和失败结果均已实现。
- [ ] MUST：需求中的字段、筛选、排序、分页、批量操作和权限差异没有遗漏。
- [ ] MUST：页面不存在无响应按钮、占位链接、假数据或未说明的临时逻辑。
- [ ] SHOULD：复杂页面维护“需求 → 路由 → API → 测试”追踪记录。

### 4.2 页面状态

每个有远程数据的页面必须检查：

- [ ] MUST：首次加载状态；
- [ ] MUST：有数据状态；
- [ ] MUST：空数据状态；
- [ ] MUST：请求失败状态；
- [ ] MUST：无权限状态；
- [ ] MUST：数据失效或关联对象已删除状态；
- [ ] MUST：后台刷新状态；
- [ ] MUST：提交中、成功和提交失败状态；
- [ ] SHOULD：部分数据加载失败时允许其余内容继续使用。

首次无缓存时使用与最终布局接近的 Skeleton。存在可用缓存或旧数据时采用 stale-while-revalidate，不得退回全屏 Loading。

### 4.3 核心业务流程

- [ ] MUST：用户可以从正常入口完整走通核心流程。
- [ ] MUST：刷新页面、浏览器返回和直接打开深链接后，流程状态可正确恢复。
- [ ] MUST：重复点击或网络重试不会产生重复写入。
- [ ] MUST：提交期间有明确反馈，并防止不允许的重复提交。
- [ ] MUST：服务端拒绝操作时，前端显示准确、可恢复的反馈。
- [ ] MUST：乐观更新失败时可以回滚或重新获取权威数据。
- [ ] SHOULD：长任务支持查看进度、离开页面后恢复、失败重试或取消。

## 5. 路由与导航门禁

- [ ] MUST：所有正式路由均可直接访问和刷新。
- [ ] MUST：动态路由参数经过校验，不存在时进入明确的 404 或资源不存在状态。
- [ ] MUST：登录失效后保存安全的返回地址，重新登录后可恢复合理位置。
- [ ] MUST：无权限访问显示 403/无权限界面，不能伪装成空数据。
- [ ] MUST：面包屑、侧边栏选中态和页面标题与当前路由一致。
- [ ] MUST：浏览器前进/后退不会造成筛选条件和 UI 状态错乱。
- [ ] SHOULD：分页、筛选、搜索等需要分享或恢复的状态存入 URL。
- [ ] SHOULD：离开有未保存内容的页面前给出确认提示。

## 6. API 与数据集成门禁

### 6.1 契约

- [ ] MUST：请求和响应类型与后端契约一致。
- [ ] MUST：外部响应先按 `unknown` 处理并在边界完成必要校验。
- [ ] MUST：后端 DTO 经 Mapper 转换后再进入领域或展示模型。
- [ ] MUST：UI 不根据后端自然语言错误文案编写程序分支。
- [ ] MUST：错误分支依据稳定错误码、HTTP 状态和结构化字段处理。
- [ ] MUST：分页、排序、时区、时间格式、金额单位和枚举映射明确。
- [ ] MUST：新增或变更字段具备向后兼容策略，或同步完成版本升级。

### 6.2 请求行为

- [ ] MUST：请求支持超时或可取消机制，组件卸载后不写入失效状态。
- [ ] MUST：401、403、404、409、422、429 和 5xx 有明确处理策略。
- [ ] MUST：自动重试只用于安全、幂等的请求；写请求不得盲目重试。
- [ ] MUST：搜索、自动保存等高频请求具有防抖、取消或顺序保护。
- [ ] MUST：旧请求晚返回时不能覆盖新请求结果。
- [ ] SHOULD：相同查询避免无意义重复请求，并有明确缓存失效策略。

## 7. CQRS 与异步任务门禁

驾驶舱、项目工作台、我的待办以及其他投影页面必须遵守：

- [ ] MUST：命令成功与读模型更新成功是两个不同状态。
- [ ] MUST：实现 `fresh / syncing / delayed / failed` 四类投影反馈。
- [ ] MUST：正常投影窗口内保留旧数据或展示可回滚的乐观数据。
- [ ] MUST：超过约 2.5～3 秒未确认时显示延迟提示，而不是业务失败。
- [ ] MUST：超过重试上限后保留最后可用数据并提供手动重试。
- [ ] MUST：页面刷新后能够从服务端重新确认真实状态。
- [ ] SHOULD：使用 `eventId`、版本或投影 watermark 判断 read-your-writes。
- [ ] SHOULD：轮询采用有限退避；有 SSE/WebSocket 时处理断线与重连。

AI 生成、渲染、发布等长任务还必须满足：

- [ ] MUST：区分排队、运行、暂停、完成、失败、取消等状态。
- [ ] MUST：页面重新进入后可以恢复任务状态。
- [ ] MUST：失败信息可理解，并提供允许的后续操作。
- [ ] MUST：前端不会因轮询重复创建任务。

## 8. 表单与用户输入门禁

- [ ] MUST：必填、长度、格式和业务校验结果明确展示。
- [ ] MUST：客户端校验用于即时反馈，但不替代服务端校验。
- [ ] MUST：服务端字段错误可以定位到具体控件；全局错误显示在表单级区域。
- [ ] MUST：提交失败后保留用户已输入内容。
- [ ] MUST：提交成功后关闭、重置或保留表单的行为符合产品约定。
- [ ] MUST：按钮禁用不能成为唯一解释，必须让用户知道为什么不可操作。
- [ ] MUST：文件上传校验类型、大小、数量，并展示进度和失败状态。
- [ ] SHOULD：长表单提供草稿、自动保存或离开确认。
- [ ] SHOULD：敏感字段避免被日志、URL、埋点和无关缓存记录。

## 9. 权限与前端安全门禁

- [ ] MUST：前端权限控制只用于交互呈现，不被视为安全边界。
- [ ] MUST：无权限操作不显示或明确禁用，服务端拒绝后仍有正确反馈。
- [ ] MUST：Token、密钥和内部服务地址不得进入客户端 Bundle。
- [ ] MUST：用户生成 HTML、Markdown、富文本和 URL 在渲染前经过安全处理。
- [ ] MUST：外部链接、下载和新窗口行为符合安全属性要求。
- [ ] MUST：日志和错误上报不包含 Token、密码、身份证号等敏感数据。
- [ ] MUST：Server Component 传给 Client Component 的数据可序列化且不包含服务端秘密。
- [ ] SHOULD：依赖安全扫描没有未处置的高危问题。

## 10. UI、主题与可访问性门禁

- [ ] MUST：符合统一 UI 设计规范中的令牌、布局、密度和组件归属要求。
- [ ] MUST：`light`、`dark` 和 `system` 三种选择模式均验证；`system` 正确跟随操作系统。
- [ ] MUST：新增语义令牌同时定义亮色和暗色值。
- [ ] MUST：核心流程可仅使用键盘完成，焦点顺序与视觉顺序一致。
- [ ] MUST：状态不只依赖颜色表达。
- [ ] MUST：控件有可访问名称，表单错误与字段正确关联。
- [ ] MUST：触屏环境中关键操作不依赖 hover。
- [ ] MUST：文本放大到 200% 后不丢失内容或功能。
- [ ] MUST：动态反馈使用合适的 `aria-live`，不会重复或过度播报。
- [ ] MUST：动效尊重 `prefers-reduced-motion`。

## 11. 兼容性与响应式门禁

项目目标浏览器以 `frontend/package.json` 的 `browserslist` 为准：

- Chrome ≥ 109；
- Edge ≥ 109；
- Firefox ≥ 115；
- Safari ≥ 16。

验收要求：

- [ ] MUST：核心流程至少在目标浏览器代表版本完成验证。
- [ ] MUST：最小工作视口 1366×768 下不存在关键内容遮挡或无法操作。
- [ ] MUST：浏览器缩放 100% 和 200% 时核心功能可用。
- [ ] MUST：横向滚动只出现在表格、时间线等明确允许的局部容器中。
- [ ] MUST：长文本、多语言字符、空值和极端数值不会破坏布局。
- [ ] SHOULD：低于最小工作视口时提供可理解的兼容提示，而不是静默失效。

## 12. 性能门禁

### 12.1 用户体验预算

在生产等价环境、目标桌面设备和稳定网络条件下，关键页面采用 Core Web Vitals 的“良好”阈值作为默认预算：

- LCP：p75 ≤ 2.5 秒；
- INP：p75 ≤ 200 毫秒；
- CLS：p75 ≤ 0.1。

如测试环境无法形成可靠 p75 样本，发布前至少记录 Lighthouse/浏览器性能基线，并确保相对上一个正式版本没有未经批准的显著回退。

### 12.2 实现要求

- [ ] MUST：首屏没有全屏 Loading 闪烁或明显布局跳动。
- [ ] MUST：Skeleton 尺寸接近最终内容。
- [ ] MUST：Client Component 边界保持最小，不因局部交互将整个页面客户端化。
- [ ] MUST：大型编辑器、图表、媒体工具和非首屏弹窗按需加载。
- [ ] MUST：图片声明合理尺寸并按场景压缩、懒加载。
- [ ] MUST：列表数据量大时使用分页、虚拟化或其他受控渲染方式。
- [ ] MUST：轮询页面在不可见或不需要时降频或停止。
- [ ] SHOULD：每个正式版本记录关键路由的首屏 JS、Lighthouse 和 Web Vitals 基线。
- [ ] SHOULD：首屏 JS 或关键指标相对基线回退超过 10% 时必须说明原因并评审。

## 13. 错误处理与可观测性门禁

- [ ] MUST：应用级和高风险页面具有 Error Boundary 或等价兜底。
- [ ] MUST：未知错误显示用户可理解的兜底信息和恢复入口。
- [ ] MUST：错误上报至少包含路由、操作、错误码、时间和可关联请求标识。
- [ ] MUST：生产环境不向用户暴露堆栈、内部路径和服务端实现细节。
- [ ] MUST：错误上报失败不能再次导致页面崩溃。
- [ ] SHOULD：关键命令可以关联 `requestId / commandId / eventId`。
- [ ] SHOULD：监控区分代码异常、接口异常、投影延迟和用户输入错误。

## 14. 自动化质量门禁

在 `frontend/` 目录执行：

```bash
npm run lint
npm run test
npm run build
npm run test:e2e
```

要求：

- [ ] MUST：ESLint 和 TypeScript 检查通过。
- [ ] MUST：生产构建通过。
- [ ] MUST：相关单元测试和集成测试通过。
- [ ] MUST：核心流程 E2E 通过。
- [ ] MUST：不存在被意外提交的 `.only`、跳过测试或无解释快照更新。
- [ ] MUST：修复缺陷时补充能够复现该缺陷的测试，除非书面说明不适合自动化。
- [ ] SHOULD：关键页面具有视觉回归基线。
- [ ] SHOULD：测试失败时输出足以定位问题的日志、截图或 Trace。

## 15. 测试覆盖要求

必须覆盖以下高价值路径：

- 登录、退出和登录失效；
- 项目选择与项目工作台；
- 创建、编辑、删除或归档等关键写操作；
- 剧本、资产、分镜、审核、AI 任务和发布的核心链路；
- 权限不足和资源不存在；
- 网络失败、服务端校验失败和重复提交；
- CQRS 投影正常、延迟和失败；
- 亮色、暗色及 system 切换；
- 页面直接访问、刷新和浏览器返回；
- 至少一条键盘完成的核心流程。

不要求追求形式上的 100% 覆盖率，但关键业务规则、错误分支和历史高频缺陷必须被测试保护。

## 16. 生产构建与配置门禁

- [ ] MUST：开发、测试和生产 API 地址通过环境配置提供，不硬编码在组件中。
- [ ] MUST：客户端环境变量只包含允许公开的信息。
- [ ] MUST：缺少必要环境变量时构建或启动明确失败，不静默使用危险默认值。
- [ ] MUST：生产构建不依赖本地 Mock、测试账户或开发服务器。
- [ ] MUST：Source Map、日志级别和调试工具符合生产策略。
- [ ] MUST：静态资源路径、刷新回退和缓存策略在目标部署环境验证。
- [ ] SHOULD：发布产物可追踪到 Git commit 和构建版本。

## 17. 缺陷等级与发布规则

| 等级 | 定义 | 发布规则 |
|---|---|---|
| P0 | 数据破坏、严重安全问题、应用不可用 | 必须阻断，立即修复 |
| P1 | 核心流程不可完成、普遍崩溃、严重越权或错误结果 | 必须阻断 |
| P2 | 非核心功能受损，有明确绕行方式 | 评估后决定，必须登记 |
| P3 | 轻微视觉、文案或低频体验问题 | 可带入后续迭代 |

以下问题无论缺陷等级如何，默认阻断交付：

- 生产构建失败；
- 核心 E2E 失败；
- 服务端秘密进入客户端产物；
- 目标浏览器无法完成核心流程；
- 关键数据被错误覆盖、重复创建或无法恢复；
- 存在未处置的高危安全问题。

## 19. 发布前总清单

### 功能负责人

- [ ] 需求验收条件全部通过；
- [ ] 核心业务流程和异常分支通过；
- [ ] 不存在无响应入口、假数据和阻断缺陷。

### 前端负责人

- [ ] UI、领域边界和 Next.js 边界符合规范；
- [ ] API、路由、权限、表单和异步状态完成验收；
- [ ] 性能、浏览器、主题和可访问性完成验证；
- [ ] 所有自动化质量门禁通过。

### 发布确认

- [ ] 生产配置和构建产物已验证；
- [ ] 已知问题、例外和回退方式已有记录；
- [ ] 版本号、Commit 和验收证据可以追踪；
- [ ] 交付结论明确记录为“通过”或“阻断”。

## 20. Definition of Done

一个前端功能只有在以下条件全部成立时才算完成：

> 功能符合验收条件，数据和异常状态完整，UI 与领域边界符合规范，目标浏览器和主题可用，核心流程测试通过，生产构建成功，且没有阻断交付的已知缺陷。
