# 运行与发布就绪基线

> 适用范围：Manju 正式产品从本地开发、测试、预发布到生产发布的共同基线。本文约束的是目标实现；现有代码与本文不一致时，必须通过迁移任务消除差异，不能静默降低标准。

## 1. 环境分层

| 环境 | 数据 | 外部服务 | 用途 | 发布限制 |
|---|---|---|---|---|
| local | 合成数据 | 默认 mock，可选择沙箱 | 开发与组件测试 | 禁止连接生产数据和生产密钥 |
| test | 每次可重建的合成数据 | mock/测试实例 | 自动化测试 | 迁移必须从空库和上一稳定版本各执行一次 |
| staging | 脱敏数据或生产等比例合成数据 | 服务商沙箱 | 发布候选验证、容量验证 | 配置结构必须与生产一致 |
| production | 正式数据 | 正式服务 | 对外服务 | 仅允许已签名发布包和经验证迁移 |

任何环境都不得把访问令牌、加密密钥或用户隐私数据提交到 Git。密钥通过部署平台注入，日志只允许输出配置项名称和校验结果，不允许输出值。

## 2. 配置契约

配置项以同目录的 `environment.schema.json` 为机器可读清单。应用启动时必须完成以下校验：

1. 必填项存在，URL、整数、布尔值和枚举格式合法；
2. `DATA_ENCRYPTION_KEY` 满足当前密钥版本要求，历史密钥只用于解密；
3. 生产环境不允许通配 CORS、弱认证、关闭病毒扫描或关闭 HTTPS；
4. 外部模型、发布平台、邮件等能力未配置时必须明确标记为 `disabled`，不得延迟到首次调用才报错；
5. 配置校验失败时进程必须非零退出，健康检查不得短暂返回成功。

配置分为四类：

- 启动静态配置：端口、数据库位置、允许来源、代理和安全头；
- 密钥：JWT/SSO、数据加密、内部服务令牌、AI 和发布渠道凭据；
- 可运营配置：模型路由、预算、质检、通知、留存策略，必须进入 `typed_settings` 并有版本、审批与审计；
- 个人偏好：语言、时区、通知偏好，仅存储在用户域，不得通过进程环境变量覆盖。

## 3. 健康检查

| 探针 | 成功条件 | 失败影响 |
|---|---|---|
| `/health/live` | 进程事件循环可响应 | 编排器重启实例 |
| `/health/ready` | 数据库可读写、迁移版本兼容、关键配置有效 | 停止接收新流量 |
| `/health/dependencies` | 队列、对象存储、病毒扫描和启用的外部服务状态明确 | 降级非核心能力或阻止发布 |

依赖探针必须区分 `healthy`、`degraded` 和 `unavailable`；不得因为一个非核心 AI 服务商故障而判定整个应用不存活。数据库 schema 版本高于应用支持上限时，readiness 必须失败。

## 4. 发布顺序

1. 固化发布候选：代码提交、OpenAPI 摘要、数据库 schema 摘要和前端构建产物必须可追溯；
2. 备份：验证最近一次可恢复备份，并记录恢复演练时间；
3. Expand：只增加兼容字段、表和索引；
4. 部署兼容版本：新版本必须同时读取旧、新结构；
5. Backfill 与 shadow compare：批次可暂停、可重入，并输出差异报告；
6. 切换写入与读取：先灰度组织/项目，再扩大流量；
7. 观察稳定窗口：关键指标持续正常后才允许执行 Contract；
8. Contract：删除旧字段、旧聚合和兼容代码必须作为独立版本发布。

禁止在同一次生产发布中同时完成破坏性数据库变更和应用切换。详细批次及 Audio、ProjectClip 迁移见 `../03-database/01-migration-plan.md`。

## 5. 可观测性

所有请求、异步任务和领域事件必须携带 `traceId`；写命令还必须携带 `commandId`。日志采用结构化 JSON，至少包含时间、级别、服务、环境、版本、traceId、actorId（可脱敏）、projectId、operationId、result 和 errorCode。

| 信号 | 指标/维度 | 告警阈值（默认） |
|---|---|---|
| API | 请求量、p50/p95/p99、4xx/5xx，按 operationId | 5 分钟 5xx > 2% 为 P1；核心写入 > 5% 为 P0 |
| SQLite | busy 次数、写事务时长、WAL 大小、磁盘余量 | 连续 5 分钟 busy > 1%；磁盘余量 < 15% 为 P0 |
| Outbox | 最老待发年龄、失败次数、死信数 | 最老事件 > 2 分钟为 P1；> 10 分钟为 P0 |
| AI 任务 | 排队时长、生成时长、重试、服务商失败率 | p95 超 SLA 15 分钟或失败率 > 10% 为 P1 |
| 成本 | 预留与结算差、项目预算利用率、拒绝次数 | 单日差异 > 1% 或预算穿透为 P0 |
| 质检/审核 | 超时数、退回率、规则版本 | 核心成片质检超时 > 10 分钟为 P1 |
| 通知 | 投递延迟、失败、SSE 连接数 | 高优通知 5 分钟未送达为 P1 |
| 发布 | 成功、失败、未知结果、重试 | 出现 `unknown_result` 立即 P1，重复发布为 P0 |
| 备份 | 备份年龄、校验、恢复演练 | 超过 RPO 或校验失败为 P0 |

阈值是产品首发默认值，需通过受审计的配置版本调整。告警必须指向操作手册，不能只发送原始异常。

## 6. 容量与连续性目标

- API 可用性目标：月度 99.9%（计划维护窗口单独公告）；
- 核心查询 p95：正常负载下不高于 500 ms；核心命令接受 p95 不高于 800 ms；
- RPO：生产数据 15 分钟；RTO：4 小时；
- 每日增量、每周完整备份；备份加密并与主数据故障域隔离；
- 每季度至少一次恢复演练，恢复结果包含行数、附件抽检和关键聚合一致性；
- SQLite 单写节点达到已验证容量的 70% 时必须启动扩容或数据库迁移决策，不依赖临时提高超时掩盖瓶颈。

## 7. 灰度、回滚与熔断

回滚触发条件包括：核心写入 5xx 超 5%、数据一致性差异超过 0.1%、出现预算穿透、重复发布、权限越权、不可逆数据损坏，或 P0 告警持续 5 分钟。

回滚顺序：停止新命令 → 暂停 worker/outbox 消费 → 保留证据与偏移量 → 将流量切回上一兼容应用版本 → 对未确认命令按 `commandId` 对账 → 必要时按恢复点恢复。不得直接回滚已经被旧版本无法理解的 Contract 迁移；这也是 Contract 必须延后独立发布的原因。

外部 AI、邮件、发布平台失败时采用按提供商熔断、指数退避和死信处理。具有不确定外部结果的发布请求不得自动盲重试，必须先按外部幂等键查询状态。

## 8. 上线前 Go/No-Go

以下条件必须全部满足：

- OpenAPI、物理模型、页面状态和验收场景的自动校验通过；
- 后端构建、前端类型检查和受影响测试通过；
- 空库迁移、上一稳定版本升级、回滚路径和备份恢复均在 staging 演练；
- P0/P1 页面具有加载、空、无权限、冲突、失败和成功状态；
- 权限、预算、审计、通知、质检、发布幂等和删除恢复完成专项测试；
- 仪表盘、告警路由、值班人和操作手册可用；
- 未解决缺陷中无 P0/P1，P2 缺陷已有负责人、规避方案和截止日期。

上线后至少执行登录、创建项目、导入剧本、创建 Shot、生成与审核资产、编辑字幕、导出成片、通知读取、审计查询、软删除与恢复的冒烟链路。任一步骤失败则停止扩大灰度。
