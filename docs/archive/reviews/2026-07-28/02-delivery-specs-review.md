# 逐功能交付规格 Review 报告（2026-07-28）

> 范围：产品需求、页面模块、DDD 聚合、页面交互、目标 API、逻辑数据模型和 Gherkin 验收场景。  
> 结论边界：本报告证明目标设计的覆盖与一致性，不替代 OpenAPI、迁移、代码、自动化执行和用户可用性验证。

## 1. Review 方法

1. 正向从 US-001～029、MANGA-001～008、US-PM-001、US-DS-001 检查四联件。
2. 反向从 `06-module-map.md` 的页面和各 DDD 聚合检查无需求编号的隐性功能。
3. 对每个功能检查正常、负向、权限/范围、并发/幂等、异步失败/恢复场景是否适用且存在。
4. 检查 API 版本、统一错误、If-Match、Idempotency-Key、数据事实源、不可变版本、软删和审计规则。
5. 自动检查 ID 覆盖、场景唯一性、相对链接、Markdown 表格、UTF-8 和 Git diff 空白错误。

## 2. 第一轮发现与修复

| 发现 | 风险 | 修复 |
|---|---|---|
| 39 条显式需求都有规格，但页面/聚合仍存在无编号能力 | 无法真正宣称“逐个功能”，实现证据无处回填 | 新增 CAP-001～008：成员、模型、流水线、数据集、对话、任务运维、预算、质量规则 |
| 项目成员权限只散落在 Project 与 RBAC | 所有权转移、deny 和成员移除缺少页面/API/用例 | 新增 CAP-001，定义唯一 owner、权限解释和转移事务 |
| 模型、Pipeline、Dataset 有页面和聚合却无独立交付定义 | 管理端容易只做 CRUD，不做验证、版本和授权 | 新增 CAP-002～004 |
| AI 对话/Studio 与生成任务边界未成为可测试功能 | 消息可能成为第二份生成事实源 | 新增 CAP-005，明确 Conversation 引用 AITask |
| AI 任务队列只有生成需求中的状态说明 | 取消、重试、未知结果、人工接管不可验收 | 新增 CAP-006 |
| 预算和质量规则只有领域设计行 | 缺少具体配置页面和 API | 新增 CAP-007～008 |

## 3. 第二轮发现与修复

| 发现 | 风险 | 修复 |

## 6. 使用方式与下一门禁

开发拆卡必须引用一个功能 ID 和至少一个 Scenario ID。实现完成后按以下顺序回填：

1. OpenAPI operationId 与 Schema；
2. 数据库 migration ID、约束和回滚；
3. 前端路由/组件和权限键；
4. 契约、集成、E2E、安全或恢复测试路径及运行结果；
5. `11-traceability-matrix.md` 与 `03-feature-status.md`。

任何一项缺少真实证据时只能称为“设计完成”，不能称为“功能完成”。

## 7. Review 结论

当前已形成逐功能、可追踪、可拆卡、可转自动化测试的目标交付契约；本轮发现的覆盖缺口和内部矛盾均已修正。就当前冻结需求与正式模块范围，未发现仍未处理的文档级 P0/P1 缺口。

这不是“代码 100% 无问题”的证明。OpenAPI、数据库、现有实现和真实用户操作尚未按这些场景执行，因此实现状态必须继续保持待核验。
