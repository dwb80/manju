# 产品级需求审计

> **基线日期**：2026-07-28  
> **审计口径**：判断是否形成“需求—领域—接口—实现—验收”闭环；代码或页面存在不等于产品需求完整，需求分散也不等于能力完全不存在。

## 1. 总结

现有文档已经覆盖主生产链路，并存在认证、通知、回收站、设置、审计、导入导出和备份的不同程度实现或设计。主要问题不是简单的“模块数量不足”，而是：

- 漫剧专业语义弱，核心模型仍偏通用视频生产。
- 产品需求散落在总纲、模块指南、API、DDD 和代码中，用户故事并非完整入口。
- 文档设计领先于实现，追踪矩阵大量项目仍待核验。
- 横切能力已有局部实现，但缺少统一范围、权限、异常和验收契约。
- 领域字符串错误码和传统数字错误码并存。
- 历史模型与新 DDD 模型存在迁移和兼容债务。

因此不采用主观总分。每个能力必须以证据门禁独立判定。

## 4. 关键冲突

### 4.1 产品级与 MVP 口径冲突

需求和产品总纲仍将 P0 描述为“MVP 核心”，而产品定位是正式企业级生产平台。本轮统一改为：P0 是首个正式发布的阻断能力，不能以原型或主路径可用降格验收。

### 4.2 权限模型冲突

- 产品/DDD：项目内可组合业务角色。
- 当前认证：组织级 `admin/editor/viewer`。
- 当前项目类型：`owner/editor/reviewer/commenter/viewer`。

必须明确“系统角色”和“项目角色”是两层模型，并通过迁移消除项目角色的旧枚举。

### 4.3 错误码冲突

- 领域层：稳定字符串机器码。
- 传统路由：数字业务码。
- 需求文档：同时描述大写名称和数字编号。

目标契约采用稳定字符串 `code`；HTTP status 表达协议语义；过渡期数字码只能位于可选 `legacyCode`，不得继续复用 `code` 字段。

### 4.4 “已设计”和“已交付”冲突

DDD整改已经补齐多个结构，但 `feature-status.md` 和追踪矩阵仍将实现标记为未核验。发布计划必须按能力逐行补充代码、API、Schema、迁移、测试与监控证据。

## 5. 需求整改顺序

1. 确认产品决策 PD-001～PD-007。
2. 将漫剧专业需求、用户旅程和权限矩阵评审冻结。
3. 回写 `requirements-and-acceptance.md` 的正式 Epic/US/AC。
4. 根据需求调整 DDD 聚合、命令、事件和事务契约。
5. 统一错误、角色、通知、配置和审计的横切契约。
6. 填充追踪矩阵并形成实现差距清单。
7. 实施迁移与代码整改；自动化验收通过后更新功能状态。
